# CloudSprocket v0.4 — LocalStack Superpowers (implementation plan)

Status: planning. Target: v0.4 (current shipped: v0.3.0 on `dev`).
North star: local-first cloud workbench; lean into the IaC + LocalStack-superpowers spine.

This plan is implementation-ready for an agent (Grok) to build from. It is grounded in the
current LocalStack APIs (verified via LocalStack docs, 2026-06-15). Three features, each
independently shippable. Build per module, commit atomically (conventional-commit style, no
Claude co-author trailer), one branch off `dev` (e.g. `feat/v0.4-localstack-superpowers`),
PRs reviewed before merge.

---

## Shared context (read first)

- **Where LocalStack lives in code:** `backend/daemon/internal/localstack/manager.go` already holds
  a `Manager` with `settings config.Settings`, an `httpClient *http.Client`, a `healthEndpoint`
  (`http://localhost:4566/_localstack/health`), and Docker lifecycle (start/stop/status/logs). The
  emulator endpoint base is `http://localhost:4566`. Auth token handling already exists
  (`localStackEnv` injects `LOCALSTACK_AUTH_TOKEN` from start options or env).
- **RPC pattern:** all backend calls are dispatched in `internal/app/service.go` `Handle()` via a
  `switch method`. Add new methods like `localstack.pods.list`. Long operations run as background
  jobs that emit `job.updated` events (see `deployments.plan`). Frontend wrappers + a browser mock
  live in `apps/desktop/src/lib/backend.ts`; events bridge `.`→`:` automatically.
- **Frontend pattern:** views in `apps/desktop/src/views/`, added to the rail/nav in `App.tsx`
  (see how `DeployView` + the "Deploy" rail entry are wired). Use shadcn/ui + lucide + sonner.
- **All three features require LocalStack Pro** (auth token). Gate the UI: if no token / not Pro,
  show an explanatory empty-state (mirror the existing `requiresPro` recipe badge pattern), do not
  hard-fail. Detect via the existing token plumbing; surface a "needs a LocalStack Pro/Team token"
  notice.
- **Reachability:** reuse the deploy preflight idea — probe `_localstack/health` before any call;
  if LocalStack is not running, show "Start LocalStack from Local Runtime first."
- **Verify each module:** `go test ./...`, `pnpm run typecheck:desktop`, `pnpm --dir apps/desktop test`,
  `pnpm run build:desktop:exe`. Add Go tests with an `httptest` server for the HTTP APIs and a
  browser mock for the frontend.

Suggested home in the UI: a new **"Local Lab"** (or extend **Local Runtime**) section with three
panels — Cloud Pods, Chaos, IAM Policy Stream — visible when LocalStack is running.

## Feature 1 — Cloud Pods (save / load / list / delete local state)

**Goal:** snapshot the running LocalStack state, name+version it, reload it, share it. The killer
use: capture a deployed recipe's state as a pod, reload instantly instead of re-applying.

**Grounded API:** Cloud Pods are driven by the LocalStack CLI (`localstack pod ...`), which needs
`LOCALSTACK_AUTH_TOKEN`. Commands:
- `localstack pod save <name> [--message <msg>]`
- `localstack pod load <name>[:<version>]`
- `localstack pod list`
- `localstack pod versions <name>`
- `localstack pod delete <name>`
There is also a Python SDK (`localstack.sdk.pods.PodsClient`) and a platform REST backend, but the
CLI is the simplest, documented path.

**Backend (daemon):**
- New `internal/localstack/pods.go`. Shell out to the `localstack` CLI exactly like the tofu/az
  runners do: `exec.CommandContext`, then `sysproc.Hide(cmd)` (Windows no-console), env with
  `LOCALSTACK_AUTH_TOKEN` from settings/start options. Parse `list`/`versions` output — prefer a
  JSON flag if available (`--format json`), else parse the table.
- Resolve the `localstack` CLI like tofu is resolved (PATH first). If absent, return an actionable
  error ("LocalStack CLI not found; install with `pip install localstack`"). Consider documenting
  this as a prerequisite rather than auto-installing for the MVP.
- RPCs in `service.go`: `localstack.pods.list`, `localstack.pods.save` (background job, streams
  progress), `localstack.pods.load` (background job), `localstack.pods.delete`. Reuse the job/event
  machinery.
- Tests: a fake CLI runner (interface like `tofu.Runner`) returning canned output; assert parse +
  RPC wiring. Gate any live test behind an env flag (`LOCALSTACK_PODS_LIVE`).

**Frontend:**
- A "Cloud Pods" panel: list (name, max version, last change), a "Save snapshot" action (name +
  optional message), per-pod "Load" and "Delete", and a versions drill-down.
- Confirm before Load (it overwrites running state) and Delete. Toasts on success/failure.
- `backend.ts` wrappers + mock pods.

**Acceptance:** with a Pro token and LocalStack running, save a pod after deploying a recipe, see it
listed, reload it into a fresh instance, delete it. Without a token: clear gated empty-state.

## Feature 2 — Chaos engineering panel (faults + latency)

**Goal:** inject AWS-service faults and network latency to test recipe/app resilience locally.

**Grounded API (pure HTTP on `:4566`, the daemon can call directly via its `httpClient`):**
- **Service faults:** `…/_localstack/chaos/faults`
  - `GET` current rules, `POST` replace-all (array), `PATCH` add a rule, `DELETE` remove a rule.
  - Rule schema: `{ "region"?, "service"?, "operation"?, "probability"? (0..1, default 1),
    "error"?: { "statusCode"? (default 503), "code"? (default "ServiceUnavailable") } }`.
  - `POST []` clears all faults. `[{}]` faults *everything*.
- **Network latency:** `…/_localstack/chaos/effects` — `GET`, `POST {"latency": <ms>}` (0 = off).

**Backend (daemon):**
- New `internal/localstack/chaos.go` with typed methods `GetFaults`, `SetFaults`, `AddFault`,
  `RemoveFault`, `GetLatency`, `SetLatency`, `ClearAll`. Use the manager's `httpClient` against
  `settings`-derived base URL. Model the rule struct in `internal/models`.
- RPCs: `localstack.chaos.get`, `localstack.chaos.setFaults`, `localstack.chaos.addFault`,
  `localstack.chaos.removeFault`, `localstack.chaos.setLatency`, `localstack.chaos.clear`.
- Tests: `httptest` server asserting the exact JSON bodies/verbs for each operation; round-trip
  GET after POST.

**Frontend:**
- A "Chaos" panel with:
  - Quick templates (mirror LocalStack's dashboard): "Service unavailable (503)", "500 internal
    error", "Region outage", "DynamoDB throttling", "Kinesis throttling", each a one-click rule.
  - A custom rule builder: service / region / operation / probability slider / status code + code.
  - A latency slider (0–10000 ms) with sensible marks (5 / 50 / 500 / 1000 / 10000).
  - Active-rules list with per-rule remove + a prominent "Clear all faults" button.
- Make it obvious chaos is ACTIVE (banner/badge) so a user doesn't forget faults are on.
- `backend.ts` wrappers + mock.

**Acceptance:** add an S3 us-east-1 fault, confirm an S3 call in that region fails (or just that
`GET faults` reflects it), add 500ms latency, clear all. Verified via the panel + a Go httptest test.

## Feature 3 — IAM Policy Stream (generate least-privilege policy, bake into recipe)

**Goal:** run a recipe deploy locally, capture the exact IAM permissions it needed, and surface a
merged least-privilege policy the user can copy or **bake into the recipe**. This is the
differentiated feature — it closes the loop between "deploy locally" and "ship hardened to cloud".

**Grounded API:**
- Requires LocalStack started with `IAM_SOFT_MODE=1` (log violations without blocking) and `DEBUG=1`.
  The existing LocalStack `Start` env builder (`localStackEnv`) should set these when an
  "IAM policy capture" mode is enabled (new start option / toggle).
- The stream itself: `localstack aws iam stream` (CLI) emits, per API call, the principal/resource
  and a suggested policy; the Web App shows a **merged summary policy**. Enforcement modes
  (`ENFORCED` / `SOFT_MODE` / `DISABLED`) are controlled by `ENFORCE_IAM` / `IAM_SOFT_MODE`.
- MVP-pragmatic path (avoid a long-lived CLI stream process): run a deploy/apply with soft-mode on,
  then read the generated policy. If a stable read endpoint isn't exposed, shell out to the
  `localstack aws iam stream` for the duration of the apply and collect its output. Validate the
  exact mechanism against the installed LocalStack version before building; prefer an HTTP/SDK read
  over screen-scraping if one exists in the target version.

**Backend (daemon):**
- New `internal/localstack/iam.go`: `SetMode(mode)`, `GetStatus()`, and `CapturePolicies()` (collect
  the generated summary policy for the current run). Mode toggling sets the env on (re)start of the
  managed container — note this requires a container recreate (the manager already recreates on
  config change).
- Integrate with deploy: an opt-in "Capture IAM policy" toggle on the deploy configure screen →
  starts LocalStack in soft mode → after apply, fetch the merged policy → attach it to the
  deployment record (new field) and surface it in the deployment detail.
- "Bake into recipe": write the captured policy into the recipe workspace (e.g. an
  `iam_policy.json` the recipe's role can consume) and/or offer it as a downloadable/copyable block.
  For the MVP, copy/show is enough; writing back into bundled recipes is a stretch goal.
- RPCs: `localstack.iam.getStatus`, `localstack.iam.setMode`, `localstack.iam.capture`.
- Tests: httptest/fake-CLI for status+capture; a deploy test that asserts the captured policy lands
  on the deployment record when the toggle is on.

**Frontend:**
- An "IAM Policy Stream" panel: enforcement mode selector (Disabled / Soft / Enforced) with a clear
  explanation of each; a "Capture from last deploy" view showing the merged policy (syntax-styled,
  copyable, reuse the OutputRow Copy button); and the deploy-screen "Capture IAM policy" toggle.
- `backend.ts` wrappers + mock policy JSON.

**Acceptance:** with soft mode on, deploy the serverless recipe, see a generated least-privilege
policy (Lambda/DynamoDB/S3/APIGW actions) you can copy. Without a Pro token: gated empty-state.

## Sequencing & conventions

1. **Chaos first** — pure HTTP, no CLI dependency, smallest blast radius, fully testable with
   httptest. Good momentum + proves the "Local Lab" panel shell.
2. **Cloud Pods** — CLI shell-out + job streaming; reuses deploy-job machinery.
3. **IAM Policy Stream** — most design risk (verify the read mechanism on the live version first);
   highest payoff. Do last, integrate with the deploy flow.

Conventions: branch `feat/v0.4-localstack-superpowers` off `dev`; atomic conventional commits
(`feat(daemon):`, `feat(desktop):`), no Claude co-author trailer; British English in copy; never
echo the real `LOCALSTACK_AUTH_TOKEN`; rebuild the exe after each module; verify with the four-check
gate; PR into `dev` for review.

## Out of scope for v0.4 (later themes)

- AWS replicator (mirror real cloud → local), App Inspector observability panel, ephemeral cloud
  instances — Theme B leftovers for v0.5+.
- Recipe registry, drift/update/cost(Infracost)/policy(OPA) — Theme A, v0.5.
- Cloud breadth (more AWS services, Azure depth, GCP) — Theme C, v0.6.
